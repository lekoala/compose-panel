# ADR 0042 — Managed site ownership and generated Compose

Status: Accepted (pilot scope)

## Context

Compose Panel administers existing Compose directories: the raw files are the
source of truth, they are edited byte-for-byte (ADR 0004), and every action goes
through the `ComposeProvider` with an explicit project identity (ADR 0005,
ADR 0008). It can create an empty stack (ADR 0024) and route a domain to a
loopback-bound service (ADR 0030), but it never generates or owns a stack.

Serving one PHP site therefore still means hand-writing Compose, a web server
configuration and a release layout, then repeating the same work for the next
site. Two documented non-goals stand in the way: generated
templates/catalogues and broader file generation (`product.md`), and the absence
of an orchestrator (`architecture.md`).

This ADR admits one narrow case and keeps the rest closed: a versioned, bounded
manifest that either opts an existing hand-written stack into one bind-mount
release layout, or that the panel uses to generate one fixed PHP profile. Both
produce an ordinary Compose directory that `docker compose` can run without the
panel.

## Decision

### One managed-site mode, two ownership values

A **managed site** is a stack directory carrying `compose-panel-site.json`
next to `compose.yaml`. The manifest is trusted operator configuration, like
`compose.yaml` itself: it is not a security boundary against anyone who can
write it. It lives outside the checkout, so repository content can never choose
mounts, paths, images or destinations.

| `owner` | Compose file | Who may edit it | Increment |
| --- | --- | --- | --- |
| `opt-in` | hand-written by the administrator | the existing raw editor | first |
| `managed` | generated by the panel from the manifest | the panel only; raw save refused | with the creation form |

Both values produce the same thing: a single-file Compose project (ADR 0004)
with an explicit project name, runnable by the Compose CLI, plus an owned
release layout and a deploy contract (ADR 0043). A managed site is **not** a
second orchestration engine.

A directory without a valid manifest is an ordinary stack and keeps every
current behavior. A manifest that fails validation never produces a partially
managed stack: the stack stays readable with a warning and site operations are
refused.

### Manifest: one path, one version, strict fields

- Fixed path `<stack>/compose-panel-site.json`; a regular file, never a
  symlink, at most 64 KiB, parsed once as UTF-8 JSON.
- Strict and versioned: `version` must be `1`, `2` or `3`; a manifest carrying
  the `database` block needs at least `2` (ADR 0048), and one carrying `backup`
  or `ci` needs `3` (ADR 0049, ADR 0050). Unknown or duplicate keys, wrong types
  and out-of-range values are refused. A future schema is a deliberate
  `version` change, never an ignored field. The panel never rewrites the
  manifest in `opt-in` mode.
- No secret value ever appears in it; it is not rendered into HTML without
  escaping and is never logged.

v1 fields (all bounded):

| Field | Required | Rule |
| --- | --- | --- |
| `version` | always | `1`; at least `2` with `database`; `3` with `backup` or `ci` |
| `siteId` | always | opaque, immutable, `^[a-z0-9][a-z0-9-]{2,63}$`; never derived from the domain or folder, so a domain change never moves data |
| `owner` | always | `"opt-in"` or `"managed"` |
| `project` | always | the exact Compose project name; never assumed from the folder name |
| `services.gateway` | always | service name that publishes the site HTTP endpoint |
| `services.runtime` | always | service name that runs PHP and must be recreated after a switch |
| `publicRoot` | always | `"public"` only in v1, relative to the release root |
| `runtime.profile` | always | `"php-front-controller"` only; a later profile is a new accepted value, not a free-form string |
| `runtime.image` | `managed` only | explicit reference from an allow-listed channel; in `opt-in` mode the Compose file owns the image |
| `database` | optional | `kind: "existing"`, an allow-listed `engine` (`mariadb`, `mysql` or `postgresql`) and one bounded external `network` name; requires `version: 2` (ADR 0048) |
| `database.network` | with `database` | exact external Compose network shared with the operator-provisioned database; only the runtime service joins it |
| `backup` | optional, `managed` only | `kind: "restic"`, one `rest:https://host/path` repository (or `rest:http://` on a loopback/single-label private host) and an optional `sql { engine: "mariadb", database }` that must match `database.engine`; requires `version: 3` (ADR 0049) |
| `backup.sql.database` | with `backup.sql` | one bounded SQL identifier; the only database the dump may select |
| `backup.trigger` | optional, `managed` only | `kind: "token"` and `everyHours` (1–720); enables the timer backup route and the fixed `site/private/backup/trigger-token.sha256` verifier, and declares the maximum age before overdue; requires `version: 3` (ADR 0051) |
| `ci` | optional, `managed` only | `kind: "token"`; enables the machine deploy route and the fixed `site/private/ci/deploy-token.sha256` verifier; requires `version: 3` (ADR 0050) |
| `gateway.port` | `managed` only | integer in the reserved range 41000–41999; the single loopback port the generated gateway publishes |
| `deploy.kind` | always | `"bind-mount"` only |
| `deploy.git.url` | always | Fully qualified public HTTPS or private SSH URL (ADR 0047), no password or token in the URL |
| `deploy.git.ref` | always | fully qualified ref (`refs/heads/...`), never a short name or a wildcard |
| `paths` | `managed` only | declared persistent roots under `site/shared`, each written relative (`shared/...`), contained, no `..`, unique, bounded count |
| `generation` | `managed` only | `1` without a database; `2` with the database fragment; see *Generated artifacts* |

The database, backup, timer and CI fields land with ADRs 0048-0051. Health
commands and hooks get their own fields when their own ADRs land. Refusing
unknown fields is what keeps that honest.

### Layout

```text
<STACKS_DIR>/<stack>/
  compose.yaml                    # raw for an opt-in stack, generated for a managed site
  compose-panel-site.json         # trusted operator config, outside the checkout
  generated/                      # approved gateway config, managed sites only
  site/
    staging/<attempt-id>/         # private, on the release filesystem
    runtime/
      releases/<release-id>/
      current -> releases/<release-id>
    shared/                       # explicit data mounts
    private/                      # release metadata, bounded attempt records, optional Git cache
```

- `<release-id>` is a bounded safe name derived from the full commit SHA; a
  published release is immutable and is never overwritten or republished.
- `current` is the one intentional managed symlink. Its target is always the
  relative `releases/<release-id>`, it is created inside the panel-owned
  `runtime/`, and it is re-validated at every use: relative, one level, an
  existing real directory, with completed-release metadata. A release that is
  not marked complete is never activated.
- A checkout is copied into staging by the panel. Repository-supplied symlinks
  and submodules are refused in the pilot, so no repository can redirect a
  release path.
- `staging/`, `private/` and the checkout are outside every container mount.

In the pilot the layout is initialised by an explicit step: for `opt-in`
stacks, the administrator creates the four directories, one baseline release,
the `current` link and a gateway configuration that carries the fixed probe
route. The lab script in *Verification* is the reference. The panel never
adopts an unknown working tree as a release and never creates these directories
implicitly for a deployment: a missing directory or an invalid `current`
refuses the operation and names the path.

For `owner: managed`, the creation form writes the same layout (directories,
generated Compose and gateway files, trusted manifest) in a hidden
`.cp-site-<random>` draft under the stacks root, then publishes it with one
rename. The draft is never a discovered stack, so an interrupted creation is
not pilotable and a crash leaves either no visible folder or a complete one.
Creation publishes no release and starts no container. One explicit **Publish
baseline** action then fetches the configured branch into the first immutable
release and points `current` at it. It requires the site to be stopped, checks
the effective profile and Docker service state under the stack lock, never
touches a container and refuses once a pointer exists. It is retryable, so a
Git or SSH failure does not require recreating the stack folder. A deployment
still requires a provable baseline (ADR 0043).

### Mounts and the runtime shape

- Host path == container path, as required by `deploy/compose.yaml`. Mount
  `site/runtime/` read-only into the gateway and the runtime service and resolve
  `.../current/...` inside; never bind `current` itself, which pins the old
  target across a switch.
- Mounts are verified from the effective Compose config before any site
  mutation, never inferred from `deploy.kind` or a service name: both services
  must mount `site/runtime/` at the same absolute source and destination,
  read-only; no mount destination may be at or below `runtime/current` (that
  would mask the switch or the probe script); `staging/`, `private/` and the
  checkout are mounted into no service. Every service of the project is
  checked, not only the declared pair, because one extra service is enough to
  expose the tree. A parent bind (`site/`, the stack directory or any ancestor)
  is refused, as is any alias of a release path, a `tmpfs` overlay at or below
  `runtime/current`, and `volumes_from`, which mounts a path this profile
  cannot verify. Paths are compared in canonical textual form: a bind source or
  container path containing `..`, `//` or a trailing slash is refused rather
  than normalized. A stack whose editor changed one of these mounts is refused
  before any stop, even when the names and the port still match.
- The gateway resolves the runtime service through Docker's embedded DNS at
  request time (a resolver plus a variable upstream), not once at configuration
  load: a runtime recreation can change its IP while the gateway container is
  deliberately kept. The generated profile does this; an `opt-in` gateway that
  pins a static upstream address is not deployable.
- The gateway has read-only access to `public/`. The runtime service reads the
  release read-only and writes only declared `shared/` paths. Protected assets
  and secrets stay invisible to the gateway.
- One gateway and one private PHP-FPM container per site, on their own Compose
  network defined by the project. An `external: true` network is refused unless
  it is the single network declared by `database` (ADR 0048), and only the
  runtime service may join it. The gateway publishes one fixed
  `127.0.0.1:<port>`; the port is stable across activations and recreation and
  changes only with an explicit detach.
- The gateway is the application web policy: document root, rewrites, PHP
  execution, public assets, sensitive paths. The same policy holds when the
  gateway is reached directly, so the host Caddy route is not a trust boundary.
- The profile reserves exactly one fixed path, `/.compose-panel/revision`,
  mapped to a panel-written script outside `public/` in each release. It emits
  the release SHA and is the only revision probe (ADR 0043). An `opt-in` stack
  must implement the same fixed route in its own gateway configuration.

### Ownership and permissions

The pilot assumes one Linux host, one panel process and service images that
choose their own users. The release layout therefore depends on explicit
numeric facts, not on shared groups:

- The panel writes as the UID/GID of the Bun process — `root` in the documented
  deployment ([deploy/compose.yaml](../../deploy/compose.yaml)) — with a `022`
  umask: release directories `0755`, files `0644`. Publication never relies on
  a group, so the gateway and PHP images keep their default user.
- The stack directory and its parents are traversable by every service UID
  (`0755`, like a conventional `/opt/stacks`). A stack path the panel cannot
  publish into, or that a service UID cannot traverse, refuses the operation
  instead of publishing an unreadable release.
- `site/private/` and `site/staging/` are `0700`, hold attempt records and the
  checkout, and stay outside every container mount. They are never made
  readable to a service.
- A published release is never writable by a service. The pilot declares no
  writable runtime path, so `shared/` is optional and owned by the operator. The
  first profile that needs writes (uploaded assets, cache) adds bounded
  `runtime.uid`/`runtime.gid` manifest fields in the same version change and
  applies them to the declared path only. Nothing is chowned implicitly.
- The revision script is an ordinary `0644` file inside the release, so it
  follows the same rule as the code it identifies.

### Generated artifacts (`owner: managed`)

- `compose.yaml` and `generated/*` are rendered from the manifest by a
  versioned generator. Output is deterministic: declared order, no timestamps,
  no random values, no secret. Re-rendering the same manifest yields identical
  bytes.
- The creation form is the only writer of a new managed site. It renders from
  the submitted bounded identifiers (never a URL, ref, path, command or image
  supplied outside the allow-list), validates the generated Compose file in a
  hidden draft through the existing provider, and publishes the complete tree
  with one rename. Until that rename the folder is not a discovered stack.
- Generated mount paths are YAML single-quoted scalars, and a declared
  persistent root is resolved through one shared function as
  `<stack>/site/shared/...` for both the generator and the effective-profile
  check. The panel creates the directory but never chowns it.
- Every foreign scalar embedded in generated YAML or Nginx directives is
  validated first: the stack path is restricted to simple ASCII segments and
  declared paths stay under `shared/`.
- The generator version is stored in the manifest. A panel that does not know
  the version refuses every managed mutation with an actionable message instead
  of rewriting anything. Generation `2` adds the database fragment (ADR 0048);
  a site without `database` stays generation `1` with byte-identical files.
- Before any managed mutation — including ordinary stack actions such as
  Start, Stop or Restart — the panel re-renders and compares byte-for-byte with
  what is on disk. Any difference is drift: the mutation is refused server-side
  (`409`), the affected artifact is named, and only an explicit regeneration
  rewrites it. Drift is never silently repaired. Reads and writes anchor the
  `generated/` directory with a no-follow handle, so a symlinked directory
  cannot redirect either.
- Regeneration takes the stack lock, refuses a pending deploy, renders from the
  manifest and replaces only `compose.yaml` and `generated/*` atomically,
  preserving each file's mode and owner. Before a gateway-port change it
  refuses a port reserved by another managed site or published by another
  container, and refuses while any Caddy domain still routes to the site. It
  does not touch a release, the pointer or a container.
- Raw save is refused for `owner: managed`, and whenever a manifest exists but
  cannot be used. It points to the manifest. `opt-in` stacks keep the editor for
  their own Compose file; a deploy revalidates the profile and fails closed if
  it no longer matches.

### Identity, conflicts and existing boundaries

- Before every site operation the panel re-reads the manifest, re-resolves the
  effective project through the provider, and refuses a site ID or project that
  belongs to another stack, or a gateway port already reserved by another
  managed site.
- Compose project identity, working directory, `-f` files and `.env`
  interpolation are explicit and verified before the mutation, exactly as for
  every other operation.
- Domains are not stored in the manifest in v1. Routing stays a separate,
  explicit step with ADR 0030, whose uniqueness rule is the only domain check;
  the site only requires a detach before a managed Down or a port change.
- `stack.managed-by` stays informational (ADR 0025). It never grants or denies a
  site operation; the manifest does.
- An `opt-in` stack stays fully editable and deployable by the Compose CLI. The
  panel adds the release layout and the deploy action; it does not take over the
  Compose file.

### Activation and failure boundaries

The release lifecycle is ADR 0043. This ADR fixes only the site-level
guarantees:

- One modifying operation per stack, through the existing lock, project
  reservation, shutdown drain and audit trail.
- The baseline release is mandatory. Before the first stop, `current`, its
  completed metadata and the revision probe must agree on one SHA. There is no
  first deployment without a rollback target in the pilot.
- The runtime service is recreated with `--force-recreate`: a pointer switch
  changes neither the image nor the Compose configuration, so an ordinary `up`
  would keep the old container and PHP would still serve the previous release.
  The deploy verifies that the runtime container ID changed and that the
  gateway container ID did not.
- A failed activation returns the `current` pointer to the previous known
  release only when service identity and process state are certain, and probes
  the rollback before reporting it.
- A crash may leave a staging directory, an attempt record or a switched
  pointer. There is no journal, no operation queue and no replay. Bounded
  attempt records under `site/private/` are evidence for inspection, never work
  to resume.
- No automatic deletion, no attach/import of an arbitrary existing project, no
  silent conversion of an existing stack and no second runtime profile.
- Handoff (later increment): removing the manifest leaves a normal Compose
  stack with its Compose file, releases and data intact, after an explicit
  review of domain and deploy eligibility. The deployment documentation gives
  the exact `docker compose` invocation for manual operation and recovery.

### Activation gate

`COMPOSE_PANEL_MANAGED_SITES_ENABLED` (default `false`) **and** a valid manifest,
which in v1 always carries the `deploy` block. Deploy additionally requires
ADR 0043's eligibility; an image-only stack cannot be a managed site and keeps
its CI/image path. When the flag is off there is no route, no site section, no
manifest read and no extra Docker call. When the manifest is invalid the stack
stays an ordinary, read-only stack.

### Security invariants

- Paths from the manifest or the checkout are validated as relative,
  normalized and contained; no such component is a symlink; no escape from the
  site root. The one panel-owned `current` link is validated as described above.
  Staging and releases are on the same filesystem so the pointer switch is one
  rename.
- The manifest is read as a bounded regular file; the checkout is never
  executed, sourced or mounted into the panel.
- Generated files never contain a secret; secrets are provisioned by the
  operator outside the checkout, `generated/` and `public/`, with explicit
  ownership and permissions. Because the generated Compose file and gateway
  policy embed the canonical stack path, managed creation refuses a stack path
  whose segments are not simple ASCII letters, digits, dots, dashes or
  underscores; this keeps YAML and Nginx syntax unambiguous.
- Every dynamic value is escaped in HTML. Audit records the stack, site ID,
  attempt ID, SHA and outcome, never repository content or file content.
- The panel stays loopback-bound, single-process, single-host and
  single-administrator. This ADR adds no API, no scheduler and no credential
  store.

## Consequences

- A single narrow path to a working PHP site is enough; the panel does not
  become a hosting control panel: a manifest, one layout, one profile.
- `product.md` and `roadmap.md` carry the accepted scope now.
  `architecture.md`, `security.md` and `deployment.md` get their sections with
  the first implementation PR, as ADR 0030 did, so no unimplemented feature is
  advertised as delivered.
- The panel gains a bounded manifest parser, a deterministic generator (managed
  mode), drift refusal and an ownership check. It gains no database client, no
  scheduler, no arbitrary file browser, no image build and no multi-tenancy. The
  only database feature is the bounded attachment declaration of ADR 0048.
- An `opt-in` stack must provide the fixed revision route; without it a deploy
  is refused rather than verified by a weaker signal.
- Deleting a site, importing arbitrary projects, provisioned databases, live
  restore, retention automation, a panel-owned scheduler, generic webhooks and a
  second profile remain out of scope until their own ADRs. CI-triggered deploy
  is ADR 0050; timer-triggered backup requests are ADR 0051.

## Alternatives considered

- **Generate only complete stacks, never opt in.** Rejected for the pilot: the
  first increment must deploy an existing hand-written PHP Compose stack, so the
  release contract is proven before any template exists.
- **Own the Compose file in both modes.** Rejected: it would take the raw editor
  and CLI ownership away from existing stacks and silently redefine ADR 0004.
- **A database or a central site registry.** Rejected (ADR 0002): the manifest
  and the directory are the record; Docker remains the state of containers.
  A second registry could desynchronize and would need its own recovery story.
- **Store a generated-file hash instead of re-rendering.** Rejected: a stored
  hash is a second source of truth. Re-rendering from the manifest is the
  comparison, and it produces an actionable diff.
- **Keep the domain in the manifest.** Rejected: ADR 0030 already owns one file
  per domain; duplicating it would create two sources of truth for routing.
- **Mount `current` instead of `runtime/`.** Rejected: a bind mount of the
  symlink pins the old target and silently serves the previous release.
- **Store a secret value in the manifest or generated Compose.** Rejected:
  both are readable configuration; secrets stay outside the checkout and the
  generated tree.

## Verification

Unit tests: manifest bounds, version refusal, unknown/duplicate keys, field
ranges, path containment, `siteId`/project/gateway-port validation, database
engine/network validation and runtime-only network membership (ADR 0048),
deterministic generation, creation writes and modes, port reservation,
drift detection on one byte, refusal of a raw save for a managed stack,
refusal of an unknown generator version, explicit regeneration, and the
provider's forced versus non-forced recreation arguments.

Linux integration, opt-in and disposable: `scripts/managed-sites-lab/run.sh`
(manual, never in unattended CI) starts a gateway and a PHP runtime with the
layout above, then proves two local revisions, a pointer switch, the recreate
requirement (the runtime container ID changes, the gateway's does not, and only
the new process serves the switch because the runtime really loads the pinned
OPcache policy), the effective mounts (same path, read-only, nothing masking
`current`), the release readable by an unprivileged service UID, the probe
format, a rollback and the front controller serving the same SHA. It runs on
its own disposable Docker-in-Docker daemon; `bun run test:managed-sites:wsl`
runs it from Windows through WSL. Fixtures are copied into the site's
`generated/` directory because that daemon only sees the shared lab directory;
a fixture mounted from the checkout is silently replaced by an empty directory.
`scripts/managed-sites-e2e/run.sh` (`bun run test:managed-sites-e2e:wsl`) then
drives the real deploy code on a second disposable daemon and covers checklist
item 1 and the relative pointer of item 2 end to end: a real two-commit
repository, a published baseline, a full deploy, a proven no-op, a return to the
previous release, two refusals before any mutation, and two SIGKILLs that leave
the attempt marker, pointer, containers and probe for inspection. The gateway
exposure, the incomplete-release refusal and Caddy attach checks stay manual on
a VM.

VM checklist before calling the pilot done:

1. Two releases, two deployments, two distinct probe answers; the second stack
   is untouched.
2. `current` is a relative symlink; a release that is not marked complete is
   refused.
3. Compose project identity is the declared name, not the folder name, the
   runtime is mounted read-only at the same host and container path and no
   mount masks `current`, a forced recreate changes the runtime container ID
   and leaves the gateway's unchanged, and the directory still runs with
   `docker compose -f compose.yaml -p <project> up -d` without the panel. A
   parent bind (`site/` or above), an alias of a release path, a `tmpfs` at or
   below `runtime/current`, a `volumes_from` and a third service mounting site
   state are refused.
4. A copy of `generated/` edited by hand is refused as drift; the affected file
   is named and nothing runs.
5. The gateway serves `public/` only: `private/`, `generated/`, the manifest and
   the release root are not reachable, and only `/.compose-panel/revision`
   reaches the probe script.
6. The gateway's published port is a single `127.0.0.1` TCP binding, unchanged
   across activation and recreation.
7. The probe answers HTTP `200` with exactly 40 lowercase hexadecimal characters
   and one newline, and `/` serves the same SHA after activation and after a
   rollback.
8. The release tree is `0755`/`0644` and readable by an unprivileged service
   UID, `staging/` and `private/` stay `0700` and outside every mount, and the
   runtime reports the pinned OPcache policy.

## Out of scope

Attaching or importing arbitrary existing projects, automatic deletion, a
second runtime profile, database provisioning, live restore, retention
automation, a panel-owned scheduler or timer installer, generic webhooks,
direct Caddy-to-FastCGI, edge Caddy options, multiple hosts and multi-user
access. Manual offsite backup is ADR 0049; the CI-triggered deploy is ADR 0050;
the timer-triggered backup request is ADR 0051.
